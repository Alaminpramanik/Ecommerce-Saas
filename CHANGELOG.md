- **How**: Rebuilt the flip sequence around two plain `<img>` refs (`base`/`reveal`) with their `.src` set imperatively in a recursive step function, rather than React state cycling through a mapped array of stacked images — avoids any timing mismatch between "which image is next" and the clip-path animation driving it. Verified live: the nested window is clearly visible mid-reveal (confirmed via screenshot — Polaroid base photo with a smaller rounded headphones photo growing inside it), the sequence still lands back on slide 1 before expanding, cursor-follow still works on the bigger card, and reduced-motion still skips straight to a plain fade with zero console errors.

Entering the control strip while already "following" snaps the deck back to its resting row immediately, rather than waiting for the mouse-leave/idle timeout.

- **How**: Added a `CONTROL_ZONE_HEIGHT` (160px) check in the deck's `mousemove` handler; verified via inspecting actual `transform` values that thumbnails move freely in the main area but read exactly `translate(0px, 0px)` the instant the cursor enters the control strip, and confirmed clicking a thumbnail from inside that strip still changes the slide correctly.

## 2026-07-17 — Fixed: mouse-trailing thumbnails could block the Shop Now button

- **What**: The Shop Now link and slide counter are now in a higher stacking context (`z-20`) than the thumbnail deck (`z-10`), so they always win hit-testing even when a trailing thumbnail drifts underneath them.
- **Why**: User reported that when the mouse-trailing thumbnails moved over the "Shop Now" button, clicks landed on the thumbnail image instead of the button — the deck was blocking the CTA, exactly the failure mode the original feature spec had called out to avoid.
- **How (two bugs, not one)**: First fix attempt only bumped the button's own `z-20` — didn't work, because the button is nested inside a wrapper (`textRef`) that itself was tied at `z-10` with the thumbnail deck; a child's z-index can't out-rank a sibling stacking context that its own ancestor is tied with. Raising the wrapper to `z-20` fixed the stacking but would have made that (larger, full-hero-height) wrapper swallow every click meant for the thumbnails underneath it — fixed by setting the wrapper to `pointer-events-none` and re-enabling `pointer-events-auto` only on the actual CTA link. Verified via a scripted mouse-move-onto-button-then-click test (not just visual inspection) that the button now receives the click and navigates correctly, and a separate regression check confirmed the thumbnails still follow the cursor and remain clickable everywhere else.

  1. **Preloader intro** — a full-viewport warm off-white (`#e8e4dd`) layer with "ATELIER NORD" / "CURATED TECH" flanking a small centered card that flips through all slide photos (~350ms each), lands back on slide 1, then scales up to fill the viewport (GSAP, `power3.inOut`, ~1.1s) before fading out to reveal the WebGL hero already showing slide 1 — brand/tagline fade out during the expand, and the existing title/meta stagger-in only starts once the preloader finishes.   2. **Mouse-trailing thumbnail deck** — the bottom thumbnail row detaches and chases the cursor when the mouse moves inside the hero, each thumbnail lerping at a different rate (0.12→0.05) so they trail like a snake and fan into an overlapping rotated stack near the cursor when it stops; returns to the static row via GSAP after 2.5s idle or on mouse-leave. Disabled entirely on touch devices and under `prefers-reduced-motion`.
- **Why**: User-supplied, fully-specified feature brief (written as a generic "single HTML file" prompt) — adapted to this codebase's actual architecture (React component, existing three.js/GSAP setup) rather than treated literally, since there is no standalone HTML file here.
- **How / bugs caught during verification**:
  - The preloader's flip cycle originally ended on whichever slide was flipped to last, not slide 1 — since the expanding image must match slide 1 for a seamless handoff to the WebGL hero (which always opens on slide 1), the flip sequence now explicitly resets to slide 0 before expanding.
  - The mouse-follow rAF loop originally read `getBoundingClientRect()` every frame to compute each thumbnail's home position — contradicts the "no layout thrash" requirement.   - GSAP's "return home" tween initially animated from a stale internal transform cache instead of the thumbnail's actual last position (since the rAF loop writes `el.style.transform` directly, bypassing GSAP) — fixed by `gsap.set()`-syncing GSAP's cache to the real current position immediately before starting the return tween.
  - Removed `scale-105` from the active-thumbnail Tailwind class — it also writes to the `transform` property, which would have silently fought with the deck's own transform management (same class of bug hit twice earlier in this hero's development).
  - A Playwright test run appeared to show a click missing its target while the deck was actively following the cursor; verified with a raw coordinate click at the thumbnail's live position that this was a test-tooling artifact (Playwright's element-stability pre-click check doesn't like a continuously-lerping element) and not a real interaction bug — clicks work correctly for actual cursor movement.
  - Verified live: intro flip → expand → handoff is seamless, reduced-motion and touch fallbacks produce zero console errors, autoplay and manual slide changes still work after the intro completes.

## 2026-07-17 — Fixed backend-hosted product images not loading in Next.js Image, added transparent product cutouts

- **What (bug fix)**: `next.config.js` now sets `images.unoptimized: true`. Next.js's image optimizer proxies remote images server-side; inside docker-compose, the frontend container resolving `NEXT_PUBLIC_API_URL` (`http://localhost:8000`) meant it was trying to reach *itself*, not the `web` backend container, so every backend-hosted product image 500'd (`ECONNREFUSED`) and silently failed to render — this affects any real merchant-uploaded product photo, not just the demo data below.
- **What (content)**: Ran the 3 demo products' fallback stock photos through automatic background removal (`rembg`/u2net) and re-uploaded the transparent PNG cutouts as their actual product images, so the hero slider now shows real floating product cutouts with no background, as requested.
- **Why**: User wants the hero product photo to have zero visible background — that requires both a transparent-PNG source image (content fix) and confirmed the app can actually load it (the image-loading bug would have silently defeated this otherwise).
- **How**: Background removal was run as a one-off local script (not wired into the product upload flow) — future product photo uploads will still need a transparent-background source image to get this effect; ask if you want background removal automated into the merchant image-upload endpoint going forward.
